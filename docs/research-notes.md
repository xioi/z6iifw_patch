# 研究笔记：Z6II 模块加载器与录像时长

## 录像限制的实际状态链

原厂普通录像的时长常量是 `1799000` 毫秒（29:59）。Z7II 的开源实现并不是单纯修改剩余时间显示，而是在录像任务启动时更新三类状态：

- writer 配置的 `+0x5c` 时长字段；
- 父录制任务的 `+0x5c` 时长字段；
- 两套 UI 配置的 `+0xd0` 总时长字段，并发送原厂刷新消息。

时长来自原厂容量计算函数，保留存储卷、预留空间、文件数量和码率转换限制。4K 50/60p 另有帧组预算，需要单独处理。

## 已失败的 ROM 直改方案

Z6II 的 ROM 查表函数 `0x10478240` 使用与 Z7II 相同的配置索引算法，表项位于主模块偏移 `0x19cb760`、`0x19cb808`、`0x19cb8b0`。把 96 个 `1799000` 改为更大值会改变菜单预计时间，但真机开始录像立即报告“录制已中断”。99:59:59 和 9:59:59 两个版本均失败，因此不是单纯数值溢出问题，而是没有同步完整录制状态。不要继续发布该直改表固件。

## 大容量可录时间的 16 位显示回绕

512 GB CFexpress B 卡的真机反馈确认了两个精确回绕：`19:45:33` 与显示值 `93:17` 相差 65,536 秒，`73:10:38` 与 `21:34` 相差 4×65,536 秒。容量计算得到了真实值，但原厂显示快照在 `0x10555cb6` 对毫秒除以 1000 的结果执行 `UXTH`，再以 16 位写入 `DISPLAY_SNAPSHOT+0x208`；`0x105281ac` 的格式化路径也按 16 位读取，因此超过 65,535 秒会回绕。

当前按需求只在 `movie_limit_ui` 中把 UI 发布值限制为 `ML_DISPLAY_MAX_MS=59,999,000`（999 分 59 秒）。`movie_limit_record` 仍直接调用真实容量函数并写入 writer 与父任务，不使用该 UI 上限。没有保留运行时只读代码补丁、额外 GUI Hook 或控件重写。

ARM 状态链测试覆盖两组真机容量、1000 分钟边界、恰好 999 分 59 秒和普通 30 分钟：UI 均按上限或真实小值发布，writer/父任务始终保留真实容量。完整组合在 QEMU 返回 `LOADED=11`、模块返回 0，原厂竖屏 GUI 链、录像 Hook 和视频方向 Hook 均保持正确。真机大容量卡的显示和实际录像仍需验收。

## Z6II 原生 SD 加载器

加载器移植自 [JKWTCN/z7ii-extensions](https://github.com/JKWTCN/z7ii-extensions)，保留其模块校验、重定位、缓存同步和常驻分配机制，做了以下 Z6II 适配：

- 只保留一个启动 Hook，不包含 Z7II 的网格、竖屏等无关 Hook；
- 启动位置 `0x1045063c`，宿主代码追加到 `0x125147b8`；
- 在 BSS 前原有的 8 个对齐字节中存放状态指针对：`0xc18aedb8`；
- 等待应用状态 `0xc1811e50` 的就绪字段，再依次尝试读取 `B:\Z62APP.BIN` 和 `A:\Z62APP.BIN`；
- 模块魔数改为 `Z62M`，目标标识为 `0x01700062`，避免误载 Z7II 模块；
- 保留加载状态和模块返回值，便于 QEMU/调试器诊断。

Z7II 与 Z6II 的 RAM 不能统一加一个偏移。例如启动参数、应用状态和录像 UI 配置分别存在不同的额外位移；所有函数均通过原始镜像的字节匹配、调用关系和字面量池逐项核对。

## Z62APP.BIN 格式

64 字节小端头，后接 Thumb 镜像和重定位表。头包含魔数、ABI、目标、文件尺寸、镜像尺寸、BSS 尺寸、入口偏移、重定位数量和 CRC32。加载器将镜像分配到 64 字节对齐内存，把绝对内部指针加上运行时基址，清理指令缓存后调用 `z62_main`。模块返回非零时释放内存，不保留回调。

当前录像模块使用位置无关代码，没有运行时内部绝对重定位项；两个任务回调通过 PC 相对地址取得。

## 竖屏 UI 移植

竖屏模块复用 Z7II 的 `portrait_menu.c`、`portrait_probe.c` 和直方图实现，但不移植网格等其他插件。当前版本默认开启，不包含 Z7II 的扩展设置菜单和配置文件；实体 MENU、回放与 EVF 保持原厂方向。

地址通过代码指令、ROM 指针数组和运行时对象三条路径核对。关键对应包括：图形分发 `0x1054ba99 → 0x1054e7a9`、方向读取 `0x103d4097 → 0x103d67f3`、导航表 `0x123be178 → 0x123c5e24`、字体表 `0x120687d4 → 0x120791f4`。RAM 不使用统一偏移，例如显示输出地址由同结构基址推导为 `0xc181d3cc`。

QEMU 中正式初始化返回 0，图形分发、GUI 更新、触控、导航和 i 菜单切换槽均指向正确模块函数。使用编译期强制方向的临时测试模块分别验证了左右两种竖屏；LCD 截图确认拍摄信息和 4×3 i 菜单实际旋转。临时测试模块未进入发布目录。

后续根据真机反馈把顶部信息条从整排缩放改为左右半排分行，保持原图标和字号。行内位置不压缩，行起点间隔为 64 像素；已验证双列布局、i 菜单和切换到精简 DISP 后的清除过程。截图见 `images/z62-portrait-rows.png`。

EVF 支持是独立实验分支，仅覆盖拍摄信息，不旋转 EVF 的 i 菜单。实现同时检查输出场景，并在 LCD/EVF 切换时触发原厂刷新。当前 QEMU 不提供可用 EVF 画面，因此该路径必须真机验证。发布目录只保留一种默认模块配置；需要 LCD-only 回退时，通过 `build.py --portrait --movie` 重新生成，不再保留独立预编译副本。

## 竖屏触控与菜单刷新修正

- 拍摄页触控此前被 i 菜单触控 Hook 排除。现在按 `relocate_live` 的各条规则生成逆映射候选点，再执行正向映射核对；屏幕外候选点直接拒绝，避免负坐标落入原厂左侧控件分支。触屏开关、快门速度、光圈和 i 按钮已逐点通过 ARM 调用验证。
- 普通二级设置页的原厂选项区为横向 `60–660`，旧实现把它缩到 `40–440`。现在将内容区扩展到 `0–480`，全宽背景单独裁剪，底部操作提示保留原布局，触控逆映射同步更新。
- 菜单方向变化不能只修改 `layout_orientation`，也不能只调用拍摄页的 `0x10557a09`。当前在 i 菜单和三个外部设置对象的原更新回调前检查方向，变化时通过各自 `+0x18` 事件入口发送事件 `2`，再执行原更新函数。事件 `0/1` 会退出菜单，不能用作刷新。
- 已核对的更新入口为 i 菜单 `0x105c3785`、Picture Control `0x1058f3d1`、色彩设置 `0x105b8679` 和详细设置 `0x1065c4e7`；对应事件入口为 `0x105c4c1d`、`0x1059445b`、`0x105b8617`、`0x1065c46b`。初始化同时检查更新槽和事件槽，不匹配则不加载。
- QEMU 已验证 i 根菜单、普通二级页和 Picture Control 在左竖屏、右竖屏与横屏之间完整重排，保留当前菜单层级和选中项。真机方向传感器与实际触摸仍待验证。

## 竖屏候选版真机问题（`7dab6f1`）

以下问题来自提交 `7dab6f1` 对应组合模块的真机测试，尚未修复：

1. 竖屏时，快门速度、ISO 等拍摄参数按钮可以触发，但弹出的调整页面仍为横屏。
2. 竖屏时，按下曝光补偿或 ISO 物理按钮，或放大画面后，出现的相关 UI 仍为横屏。
3. 进入 i 菜单的二级子菜单后，底部「i 键返回，OK 确认」的按钮形状与文字错位。

当前竖屏适配只覆盖拍摄主界面、i 根菜单及已知设置对象。前两项涉及的参数调整页和临时曝光/放大覆盖层需要单独识别与适配，不能直接套用现有普通设置页的映射。第三项的初步排查方向是底部提示文字与背景采用了不同的缩放路径，但尚未通过绘制记录确认根因。

## 视频方向元数据移植

实现来自 Z7II 上游提交 `e507523`（`sdk/movie_rotation.h` 和 `movie_rotation_shadows.h`）。它不重编码视频，而是在文件 mux 任务打开每个文件时读取机身姿态，在关闭文件、生成视频轨头部时替换 ISO 显示矩阵。录制中的后续转动不改变已开文件，原厂分段会重新读取姿态。

Z6II 对应关系经过原厂主模块字节匹配和实际指令核对：

- mux 任务槽 `0xc1f2d84c`，原生入口 `0x104e2141`；控制槽 `0xc1811550`，运行时控制块为 `0xc1f2d858`；
- 开档与分段函数分别为 `0x104e1eb1`、`0x104e1831`，轨道构建函数为 `0x1053ba7d`，方向读取为 `0x103d67f3`；
- 复制的 Task、Close、Header 分别位于 `0x104e2140`、`0x104e1694`、`0x1053c4bc`，尺寸为 `0x418`、`0x264`、`0x7c`；
- 三段 FNV-1a 校验分别为 `0x960f4921`、`0x12db7d0a`、`0x32842c20`。Header 与 Z7II 逐字节相同，Task/Close 只有已核对的调用编码及字面量差异；
- 原生结构保持文件表基址 `0x3f0`、步长 `0x88`、上下文偏移 `0x2c` 和矩阵偏移 `0x109`。完整调用地址表在 `z62_extensions/sdk/movie_rotation_shadows.h`。

初始化在安装其他 Hook 前检查任务槽、控制槽和三段代码哈希，不匹配则返回错误，不启用功能。复制代码保留原厂事件处理和文件写入，只把开档、分段和轨道构建调用改到模块回调。

QEMU 中独立方向模块及完整组合均返回 `LOADED=11`、模块返回 0；控制块和 mux 任务入口吻合，录像与绘图 Hook 可与方向功能共存。导出的运行时代码共 68 个调用及调用桩全部通过逐条核对，未修改的指令和字面量与原厂一致。ARM 仿真实际执行 `movie_rot_track`：姿态 1/2/3 分别写入 90°、270°、180° 的 36 字节大端矩阵，姿态 0/4 保持原厂数据，写入边界没有越界。

这些结果尚未覆盖 Z6II 真机 MOV/MP4 文件、机内回放和电脑播放器。机内回放仍按原厂横向显示；真机需要分别验证两种容器、不同开档方向及原厂分段。

## 自制直方图/水平仪的兼容性处理

视频和照片真机测试随后发现自制直方图/水平仪叠加会引起粉色像素块、假死和快门禁用。仅禁止视频模式执行采样不足以保证照片模式安全，因此当前所有模块已停用整段自制叠加逻辑，GUI 更新直接交还原厂实现。原生 DISP 和水平仪仍可使用，其他竖屏功能不受影响。后续如需恢复自制叠加，需要重新核对 Z6II 的采样对象、显示缓冲和页面生命周期，不能直接沿用 Z7II 实现。

## N-Log ISP 复用与机内 10bit 评估

NLOG8 v01/v02 的同场景真机对比表明：v02 提高了亮部可用性，但更接近可拉亮的 Flat，高光余量减少。Picture Control 方向在此收敛，后续转向原生 ISP。

Z6II 的英文菜单文本不是独立 ASCII 字符串，而是连续 UTF-16LE 数据加 32 位字节偏移表。已恢复真实文本/菜单键：N-Log 文本 `0x0793`、选择键 `0x217c`，HLG 文本 `0x0794`、选择键 `0x222e`，10bit 文本 `0x072b`、选择键 `0x2178`，View Assist 为 `0x072d` 和键 `0x222f/0x2230`。另有 `Cannot record movies while N-Log is set`（文本 `0x0887`），证明录像互斥与 ISP 色调配置是两个需要分别处理的问题。当前尚未把菜单键追到具体 ISP 写入函数。

QEMU 研究已提供可测试的 MIPU 色调入口：两个 MIPU 位于 `0x20380000/0x203c0000`，R/G/B 色调表偏移分别为 `0x3900/0x3c40/0x3f80`，每表 205 个 16bit 节点，线性插值到 15bit 输入；颜色矩阵位于 `0xb00–0xb10`，RGB→YCC 矩阵位于 `0xb64–0xb74`。该模型不是完整原厂色彩证明，但足以设计“只换色调表、保留其他寄存器”的最小实验，并作为原生 N-Log 表捕获后的对照。

机内 10bit 此前暂列低优先级，现已完成一轮普通录像专查：Z6II 主/从模块只见 H.264 驱动和事件，未见 HEVC/H.265/Main10 编码路径；普通录像构造器把 H.264 profile 固定为 100。当前 QEMU H.264 SPS 为 High profile、4:2:0，`bit_depth_luma_minus8` 和 `bit_depth_chroma_minus8` 均为 0。修改 SPS 位深字段本身不会产生有效 High 10 码流。Z8/Zf 的 HEVC Main 10 依赖不同的 EXPEED 7 管线，不能直接移植。现有证据不等于证明硬件绝对无 10bit 能力；普通编码器实测和 12bit RAW 旁路结果见下节。

### 实验 1：QEMU 仅替换 MIPU 色调表（已完成）

临时在 QEMU 设备模型中加入了默认关闭的 `EXPEED_NLOG_TONE`、MIPU 任务指纹和 H.264 输入采样开关。两组均从同一原厂 1.70 主模块、`canoe.NEF`、默认设置和同一卡镜像副本启动；生成的 flash 镜像 SHA-256 均为 `1c4820fc953cbf64a862b0573bdcf9ad044a3aff7b900635df9364b5c6605a36`。普通组未启用色调替换，实验组只设置 `EXPEED_NLOG_TONE=1`。

替换在 `mipu_job_from_regs()` 之后、任务执行之前进行，R/G/B 使用相同的 205 节点表。按 `linear=knot/32768`、`y=linear×(0.18/0.088)` 生成 N-Log-like 曲线：`y<0.328` 时使用 `650×(y+0.0075)^(1/3)`，否则使用 `150×ln(y)+619`，再钳位到 10bit 并映射到 15bit 表值。没有修改颜色矩阵、RGB→YCC、增益、位深或编码器 SPS，也没有加入 Rec.2020 转换。每次替换都把色调字段清零后对其余 `MipuJob` 做逐字节断言，实验运行没有触发断言。

MIPU 跟踪中，两组共有的 `1508×846` 预览任务具有完全相同的非色调 SHA-256 `96e61a1f1816f4b8ec229e58e023dc6ec3352039c97add7605c18d6f21a6cfed`；普通/实验色调表 SHA-256 分别为 `4c38ea302cbe914dca40420597e19a36d7f2be8d1915184f9dbe57ae2185212e` 和 `adccb004902fd26e84da4de4bf4662a4b3bdda6eb865eae5e9243f6c2c5cfbf7`。索引 `0/16/64/128/204` 的普通表值为 `0/1506/8055/22949/29271`，实验表值为 `4075/4409/9240/18938/23266`。启动及录像任务的原始输入缓冲地址会随运行调度变化，因此不能用不同启动的完整任务哈希序列证明所有瞬时状态相同；这里的“只改色调”由同一次任务解析前后的断言和上述匹配任务共同验证。

编码器入口采样不以解码视频为证据，而是在 H.264 模型读取 Y/C 平面后直接计算 NV12 哈希。两组首个完整 IDR 输入均为 1920×1080、Y stride 1920、NV12 3,110,400 字节：

| 首个完整 IDR 输入 | 普通表 | N-Log-like 表 |
| --- | ---: | ---: |
| NV12 SHA-256 | `f54d30f58164c92d014d04c1c357dd872a7c3f50a64b5cdfdc453754e40a18b0` | `3a45c421161a0d1b4ede45420147e8dd98d789971784b728bc7959e651def813` |
| Y 均值 | 120.367 | 123.284 |
| Y 的 1/5/50/95/99 分位 | 16/22/104/233/242 | 37/44/114/207/215 |

逐像素比较有 `2,062,728/2,073,600` 个 Y 样本和 `893,756/1,036,800` 个色度字节变化；按普通组 256 个 Y 值分别统计实验组条件均值，结果保持非递减。普通 Y 区间 `0–31 / 32–63 / 64–127 / 128–191 / 192–223 / 224–255` 的组内均值为 `24.520→46.735 / 47.144→69.712 / 92.035→105.268 / 164.914→157.801 / 209.658→189.734 / 234.341→208.230`，确认暗部抬升且高光压缩。导出的两幅原始 NV12 转图构图一致。色度变化是因为曲线在 RGB→YCC 前分别作用于 R/G/B，并非只后处理 Y。

**验证边界：**该实验证实了“MIPU 色调表变化会传播到 H.264 模型的实际输入缓冲”，没有证明真机原生 N-Log 已工作。QEMU 场景来自静态 NEF；H.264 模型只在 IDR 帧消费像素，P 帧全部跳过。实验组后续还出现过未刷新/全零输入帧，因此数值结论只采用首个完整有效 IDR，不评价连续录像画质。模型输出仍是 8bit High 4:2:0，与机内 10bit 无关。临时插桩、NV12/PNG 和运行输出在记录结果后清理，不进入发布模块。

下一步仍是有兼容 HDMI 设备时，只读捕获普通输出与 N-Log 的真实 MIPU 表/矩阵差异；随后对编码器绑定的内录流应用最小色调子集并单独解除录像互斥，从 1080p24/25 短片开始，先不覆盖 4K60/120。

## 普通机内 10bit 与 RAW 旁路评估

### H.264/HEVC 编码路径

普通录像的真实配置链已定位到主模块：`H264EV1` 描述符在 `0x1051f370`，给出 MMIO 基址 `0x24070000` 和状态地址 `0x24070c28`；运行时键表把 `EncodeParamKey` 映射到 `0xc1d4dbac`，`EncodeContextKey` 映射到 `0xc1d4df0c`。高级入口 `0x104a4cd0` 只选择分辨率、帧率、码率和画质等参数，没有位深选项。

`0x104be39a` 构造 `EncodeParam`，其中 `0x104be3c0/0x104be3ce` 把常量 `100` 固定写入参数 `+0x60`；`0x104be748` 展开参数时，`0x104be80e/0x104be830` 将该字节写入 MMIO `0xe30`。普通 1080p25 实测同时得到 `0xe00=0x8780`、`0xe04=0x438`、`0xe14=12`、`0xe30=100`。因此这条普通内录链明确配置 High profile，而不是 High 10；已分析的构造函数没有独立 bit-depth 参数可供模块合法切换。

Z8 3.12 固件提供了反向对照：主模块存在 `AHevcDriver`、`HEVC_0/1`、`H.265/HEVC`、`HEVC Coding`、`hvc1` 和 `eDSID_Setting_H265Mov10bitToneMode` 等字符串；Z6II 主/从模块均无这些对应物。Z8 的完整 HEVC 服务不是 Z6II 中被菜单隐藏的一项设置。

不能通过把 `+0x60` 或 SPS 改为 110 来验收：QEMU 模型并不实现真实硬件 profile/位深语义，即使看到寄存器变成 110，也仍由宿主机生成原来的 8bit 码流。真正验收必须同时有 10bit YUV 输入、有效 High 10 slice 数据及独立解码器报告 `yuv420p10`；当前没有满足这些条件的实验路径。以上结论不排除未使用的硬件能力，只否定“现有普通录像参数直接开启”的假设。

### 普通录像中的 12bit RAW 实证

与编码器不同，RAW 数据已经存在于普通录像管线。FE/MIPU 模型支持 12/14bit RAW，MIPU 另有非 DPCM 输入的 RAW 复制出口。普通录像实测 MIPU0 为：`RAW_FMT=2`（打包 12bit）、帧域 `2022×1138`、输入行距 `3040` 字节、`IN_MODE=3`；`RAWOUT_CTL=2`，其 bit0 为 0，第二路 RAW 输出未启用。

通过 HMP `memsave` 从主核虚拟地址读取当前 RAW 输入，成功导出一帧 `3,459,520` 字节，SHA-256 为 `66da6079dcee35c6371d6af71cf72d86dbc5e9d58f06b05e3b7f83553361edeb`。按每两像素 3 字节解包得到 `2,301,036` 个样本，最小/最大值 `253/4095`、均值 `750.930`、1/5/50/95/99 分位 `274/291/500/1616/2039`，共 `2,445` 个不同码值；行尾 7 字节填充全零。这证明缓冲区不是空帧或伪造元数据。HMP 的 `pmemsave` 在该模型上返回全零占位，不能用于此验证。

该配置连续导出现有行距 RAW 约需 `86.488 MB/s`（`82.481 MiB/s`）；理想打包 4K24 12bit 已约 `298.6 MB/s`，尚未计入复制、封装和文件系统开销。录像模式当前读到的是 12bit，不应从静态照片支持 14bit 推导出录像也能直接输出 14bit。

因此下一阶段更合理的实验顺序是：在 QEMU 给单帧 RAWOUT 分配私有缓冲并逐字节比较；再测试短时连续环形缓冲是否丢帧；最后才实现 1080p25 的专用 RAW 文件写入和真机短录。还需解决输入环生命周期、DMA 目标所有权、掉帧检测、时间戳和文件格式。RAW 旁路会产生新的后期工作流，**不是原厂普通 MOV/MP4 直接变成 10bit**。若只接受机内可播放的标准 10bit 视频，目前仍没有可实施且已验证的路径。

### RAW12 连续旁路的真机失败（必须保留的负面结果）

测试模块 SHA-256 `e86f03f95cead2d9b40bac745fe2a6cc0edee6c3316a334d13712fdc16e21e08` 在真机 Z6II、普通 1080p30 下失败。用户在菜单选择 enable 后开始录像，live 预览严重延迟且整机无响应，REC 红点存在但右上计时保持 `29m59s` 不动，约十秒后出现大面积粉色像素噪声并自动重启；原厂 MOV 和 `.Z12` 均未生成。照片确认这不是单纯显示 ON/OFF 或文件扩展名问题。

QEMU 中能生成结构有效的 `.Z12`，不能覆盖真机的任务优先级、缓存/DMA 一致性、内存压力及原厂文件任务并发。当前尚未区分 MIPU Hook、大块缓存失效/复制、约 10MiB 帧缓冲和并发文件写入各自的影响，不能把任一因素单独称为已证实根因。该哈希及此前连续采集版本均不得继续上机，发布目录的测试副本已撤下。

后续必须从隔离实验重新开始：第一阶段只保留 MIPU Hook，禁止读 RAW 缓冲、分配帧内存和打开文件，要求原厂短 MOV 与计时完全正常；第二阶段仅在内存捕获一帧且不写卡；通过后才评估停止原厂录像后的单帧文件导出。不得直接回到“连续复制 + 原厂录像同时写卡”的版本。

### Hook-only 隔离通过

Hook-only 模块 SHA-256 `d67102a289533c1a5e5d40f0635dfd542449e6725ad5c86e3364a0a663e263e8`，仅保留双参数 MIPU Hook、诊断计数和每 10ms 唤醒的轻量 worker，不添加菜单，不读取 RAW 地址，不做缓存操作，不分配帧缓冲，不调用文件 API。QEMU 中 Hook 计数持续增长，原厂 8.16 秒 1080p25 MOV 经 FFprobe/FFmpeg 完整解码验证。

随后用户在真机普通 1080p30 下短录，确认录像、计时和操作正常，没有上一版本的延迟、花屏或重启。该结果只在所测场景排除了 Hook-only 路径，不支持恢复连续采集。下一阶段仍需坚持单帧、仅内存、不写文件。

### 单帧内存捕获通过

单帧探针 SHA-256 `00c923f00382b4dffe8bae5bba2f8c8c78feed7c8475cf3de071db8b40001b1f`，每次录像只分配一帧内存并复制一次，不重试，不写文件，停止后释放。QEMU 得到 `captured=1`、`torn=0`，缓冲 SHA-256 为 `66da6079dcee35c6371d6af71cf72d86dbc5e9d58f06b05e3b7f83553361edeb`，与直接读取 MIPU RAW 输入一致；停止后分配/缓冲指针归零。原厂 6.12 秒 MOV 完整解码通过。

真机普通 1080p30 短录再次由用户确认正常。这说明单次约 3.46MB 分配、缓存同步和复制可与所测原厂录像共存；仍不能据此推导连续复制或并发文件写入安全。下一步只能在原厂录像停止并等待文件任务退出后，尝试导出这一帧。

### 帧完成序号与真机单帧导出通过

第一版停止后导出在真机没有生成 Z12，但状态文件显示 `state=3`、`captured=0`、`torn=1`、`export_attempted=0`，因此文件系统从未收到导出请求。最后状态 `0xa` 不含帧完成位 `0x1000`，证明通用 MIPU 通知序号混入了非帧事件。改为只用 `0x1000` 更新帧序号后，真机同时生成 `RAW12000.Z12` 和 `R12S000.BIN`；随后正常场景文件为 `RAW12001.Z12`，状态为 `captured=1`、`torn=0`、`exported=1`、`export_errors=0`。

真机 Z12 为 `3,459,600` 字节，记录 2022×1138、打包 12bit、行距 3040、30000/1001fps。它仍是**一段录像只导出一帧**，不是连续 RAW 视频。旧版连续采集的花屏重启结论保持不变，不得恢复该路径。

新增 `tools/z12_to_dng.py`：解析 64 字节 Z12 头和 16 字节帧记录，将打包 12bit Bayer 样本原值写入未压缩 16bit DNG，标记 RGGB、WhiteLevel 4095、完整 ActiveArea 和默认四像素边距裁切。当前 ColorMatrix1 明确为未校准恒等矩阵，预览偏暗/偏绿不能当作已校准色彩。

实际真机样本经 FFmpeg 解码出图；DNG 像素区与 Z12 解包后的 4,602,072 字节样本 SHA-256 均为 `5475bef098fffdb8d6f0b846b8a3c8b5d03c73fabaa4854f178b788155e4aab3`。macOS `sips` 验证长时间无响应，未计入通过项。转换命令：`python tools/z12_to_dng.py INPUT.Z12 --output OUTPUT.DNG`，多帧会按序号拆成独立 DNG。

### QEMU 普通录像基线流程

以下步骤来自实际成功的 Hook-only、单帧内存捕获和停止后单帧导出实验，不是推测的启动方法。研究环境位于 `other_researches/qemu-expeed/`，需要先准备该仓库的 `.runtime/qemu-9.1.0/build/qemu-system-arm`、样片、Mtools、ExifTool、FFmpeg 和 FFprobe。以下命令从该仓库根目录执行；`MODULE` 必须指向**当前待测产物**，不能沿用旧文件名。

先退出自己启动且仍在使用 HMP 4444 端口的旧 QEMU 实例，避免把旧进程的状态当作新模块结果：

```sh
python3 hmp.py quit
export MODULE=/absolute/path/to/Z62APP.BIN
bash out/raw12_qemu/start.sh
```

`start.sh` 使用 `out/raw12_qemu/flash.img` 和 `card.img`，把模块复制为卡根目录的 `Z62APP.BIN`，并设置 `EXPEED_SCENE=out/scene_canoe.bin`、`EXPEED_IIP_PIXELS=1`、`EXPEED_H264=fe`、`EXPEED_H264_ENCODE=1`。HMP 为 `127.0.0.1:4444`，VNC 为 `:2`。更改这些输入时必须同时记录新脚本和环境。

看到 `boot completed` 后，额外等待 **12 秒墙钟时间**，先确认宿主加载状态，再输入按键。**这 12 秒必须从出现启动完成提示后开始，不能从启动命令开始计时。** 已有从启动命令计时导致尚未正常起流就发送按键、最终帧通知全为零的无效运行。以下代码通过运行时指针读取状态，并把模块基址保存为后续 dump 的输入：

```sh
sleep 12
python3 - <<'PY'
import json
import struct
from pathlib import Path
from hmp import hmp
out = Path('out/raw12_qemu').resolve()
hmp([f'memsave 0xc18aedb8 8 "{out / "anchor.bin"}"'], settle=1)
state = struct.unpack('<I', (out / 'anchor.bin').read_bytes()[:4])[0]
hmp([f'memsave {state:#x} 44 "{out / "loader-state.bin"}"'], settle=1)
image, status, result = struct.unpack_from('<III', (out / 'loader-state.bin').read_bytes(), 32)
assert status == 11 and result == 0, (hex(image), status, result)
(out / 'module-state.json').write_text(json.dumps({
    'state': hex(state), 'image': hex(image),
    'status': status, 'module_result': result,
}, indent=2) + '\n')
print(hex(state), hex(image), status, result)
PY
```

然后执行 `v` 切到视频，等待 5 秒。对 RAW12/Hook-only 实验，开始录像前必须读取当前模块符号表中的 `raw12_hook_frames`，间隔 1 秒读取两次并确认计数增长；若为 0 或不再增长，本次不能用于评价捕获算法：

```sh
python3 hmp.py 'sendkey v'
sleep 5
python3 - <<'PY'
import json
import os
from pathlib import Path
import struct
import time
from hmp import hmp
out = Path('out/raw12_qemu').resolve()
module = Path(os.environ['MODULE'])
symbols = json.loads(module.with_suffix(module.suffix + '.json').read_text())['symbols']
image = int(json.loads((out / 'module-state.json').read_text())['image'], 16)
address = image + symbols['raw12_hook_frames']
def counter():
    hmp([f'memsave {address:#x} 4 "{out / "frame-counter.bin"}"'], settle=1)
    return struct.unpack('<I', (out / 'frame-counter.bin').read_bytes())[0]
first = counter()
time.sleep(1)
second = counter()
print('frame counter:', first, second)
assert second > first, 'No advancing MIPU frames; not a valid recording test'
PY
```

只有上述检查通过才执行一次 `r` 开始录像。随后每秒读取一次 `MOVIE_ACTIVE`，最多等待 **15 秒**，直到字节值变为 1；不能固定等 1 秒就判定未激活，也不能因暂时为 0 而反复按键（会产生多段录像）。确认激活后再继续录到约 4 秒，用 `r` 停止并等待至少 9 秒。若从未观察到 1，就不发送额外的停止键，本次运行判为无效。需要诊断模块状态或抓取内存时，再让导出额外等待至少 3 秒。以下时序是墙钟等待，不要把虚拟时间戳直接当成等待命令：

```sh
python3 - <<'PY'
from pathlib import Path
import struct
import time
from hmp import hmp
out = Path('out/raw12_qemu').resolve()
hmp(['sendkey r'], settle=1)
active = 0
for _ in range(15):
    time.sleep(1)
    hmp([f'memsave 0xc18117a8 4 "{out / "movie-active.bin"}"'], settle=1)
    active = struct.unpack('<I', (out / 'movie-active.bin').read_bytes())[0] & 0xff
    if active == 1:
        break
print('MOVIE_ACTIVE:', active)
assert active == 1, 'Recording did not start; not a valid capture test'
time.sleep(3)
hmp(['sendkey r'], settle=1)
time.sleep(9)
PY
```

`v` 是照片/视频选择杆，`r` 是录像按钮，不是通用 QEMU 快捷键。若没有新的 `R12Sxxx.BIN`，还要检查原厂录像是否实际启动。不能只根据按键日志或 `LOADED=11` 宣称录像/捕获成功。若模块清单没有某个被编译器优化的局部计数符号，不要假定它仍存在；应读取实际符号或当前状态文件，不要让诊断脚本的 `KeyError` 中断录像流程。

读取主核内存必须使用 HMP **`memsave` 虚拟地址**，不能使用 `pmemsave` 代替：当前模型中后者对相关 RAM 返回全零占位。模块各变量偏移从当前 `.BIN.json` 的 `symbols` 获取，基址使用上一步保存的 `image`，不要硬编码旧基址。模块加载状态的 `+32/+36/+40` 分别为 `image/status/module_result`。记录 dump 对应的模块哈希，避免混用旧符号表。

从虚拟卡根目录读取状态的示例：

```sh
mdir -i out/raw12_qemu/card.img@@4194304 ::
mcopy -o -i out/raw12_qemu/card.img@@4194304 \
  ::R12S000.BIN out/raw12_qemu/R12S000.BIN
python3 - <<'PY'

from pathlib import Path
v = struct.unpack('<32I', Path('out/raw12_qemu/R12S000.BIN').read_bytes())
assert v[0] == 0x53323152 and v[1] == 1 and v[30] == (~v[0] & 0xffffffff)
for i, value in enumerate(v):

PY
```

状态文件编号应取本次新产生的文件，不应直接假定是 `R12S000.BIN`。Z12 还需检查每个帧记录的 magic、大小、序号和像素范围，并用 `tools/z12_to_dng.py` 实际生成和打开 DNG。原厂 MOV 要从 `DCIM` 的实际子目录取出本次新文件，使用 FFprobe 检查流信息后，再由 FFmpeg **完整解码**；以下命令中的路径必须替换为实际文件：


只有新文件、正确捕获状态、帧数据和原厂 MOV 解码均符合要求，才可宣称该次 QEMU 录像实验通过。QEMU 使用静态 NEF 场景且 P 帧模型不完整，仍不替代真机验证。

### 双帧缓冲分配诊断

双帧诊断模块 SHA-256 `ed551450208c31ce6f6412f64366224cbab7df44cbea0bfbc0590039761dcb51` 按上述基线成功启动录像，但没有导出 Z12：池 0 分配返回 0、错误码 `0x2102`，池 1 的单帧分配成功。每帧含 64 字节对齐余量的申请为 3,459,583 字节。这不是帧格式或连续性校验失败，因为尚未执行复制。

停止后写出的 `R12S004.BIN` 保存了 `0x1034c2b7(pool=0)` 和 `0x1034c2d9(pool=0)` 的原始返回值，分别为 `0x22fff0`（2,293,744）和 `0x1e9880`（2,005,120）。这两个统计字段的语义尚未核实，不能直接标为当前可用容量；特别是池 1 的返回值小于一帧申请量，但该次分配实际成功。当前双帧候选仍未通过验收，不能上机。

另一轮把两笔申请都放在池 1（SHA-256 `df9748c07cd5c1d3799ae7030c5b808556a992ca12745a4c592ced263e674bc9`），得到 `R12S005.BIN`：两笔均返回 0，统计返回值为 `0xf62798` 和 `0xf1c060`。这些变化说明不能从单次统计值推断可分配容量，也不能宣称某一个池固定可用。下一项隔离实验是在录像仍有效时有限次重试未成功的分配，只保留已成功指针，并在 `data[25]` 高 16 位记录分配轮数；失败时仍不复制、不导出。

加入最多 100 轮分配重试的 SHA-256 `21c1b25b98ce23655328f7e2f946deb5ee552f675a6cc6d3f89b09bec3b8a3ed` 在第一轮得到两个非空指针，但 `state/captured` 仍为 0。读取实际 BSS 后发现双帧初始化漏掉了 `state=1`，下一循环又回到分配路径，因此这不是捕获阶段的失败。不能把上述有指针但无帧文件的结果记作内存分配失败。

补上等待帧状态转换后的 SHA-256 `035c017384954eaa04eb83b5f8c534ca5ec687aa056657ff2e1487e61196f22e` 按基线流程通过：两个缓冲分别来自池 0/池 1，第一轮分配成功；录像期间得到 `captured=2`、`torn=0`、`rejected=0`、序号 `0x65a/0x65b`。停止后 `R12S007.BIN` 为 `state=2`、`export_attempted=1`、`exported=1`、`export_errors=0`、`dual_error=0`，`data[25]=0x00010000`（一轮分配、零次源帧重试）。`RAW12001.Z12` 为 6,919,136 字节，SHA-256 `ae5180bfff86ab68feb4fa081e7accc1b36c811fc6e57d2570024e8866c8b209`，恰好是 64 字节文件头、两个 16 字节帧头和两个 3,459,520 字节帧载荷。

两个帧载荷的 SHA-256 均为 `66da6079dcee35c6371d6af71cf72d86dbc5e9d58f06b05e3b7f83553361edeb`，与已验证单帧样本一致；各有 2,301,036 个样本、2,445 个不同码值，范围 253–4095、均值 750.930。静态 NEF 场景下两帧内容相同是预期现象，不构成真实运动画面的时间变化证明。两个 DNG 的像素均与对应 Z12 解包样本逐项一致，FFmpeg 实际出图。临时检查脚本最初误用二维数组的 `len(raw)`（行数）而非 `raw.size`（样本总数）导致断言失败；修正后通过，不是 RAW 像素故障。

同次原厂 `DSC_0008.MOV` 为 4.32 秒、1920×1080、25fps、H.264/yuv420p，FFmpeg 完整解码无错误。此结果只证明双帧内存捕获、停止后两帧导出和所测原厂短录可在 QEMU 共存；尚不是连续 RAW 视频。

同一模块在真机普通 1080p30 短录后没有 Z12，新的 `R12S000.BIN` 为 `state=3`、`captured=1`、`torn=1`、`rejected=0`、`export_attempted=0`。两块申请第一轮均成功（`0xc2d03dd8/0xc3c6f090`），宽度/高度/行距仍为 2022/1138/3040，因此不是分配或文件系统失败；第二帧复制期间触及撕裂保护，导出未启动。QEMU 的 MIPU stream 只在计时器到达时置 `MIPU_ST_FRAME_DONE`，不模拟真实 RAW 源环切换，不能覆盖该失败。撕裂诊断版 SHA-256 `1832d0bf2760a5aa5e61a1942546bdadca19578dc4bf44b88b6b4d6cc64ac363` 已按同一基线通过 QEMU 复验：`captured=2`、`torn=0`、`rejected=0`、`exported=1`，序号 `0x729/0x72a`，Z12 SHA-256 `7fa3d48077c02671cd882cc03f26254eb653270370f65cebf3e96fdc0f1ced55`；同次 4.68 秒原厂 MOV 完整解码通过。真机状态文件中 `data[22]` 为 `0x2201` 时表示复制期间帧序号变化，`0x2202` 表示源地址变化，`0x2203` 表示第二帧序号不连续；`data[23]/data[24]` 分别保存复制后的序号和源地址。此版本只定位原因，并未修复真机撕裂；撕裂时仍不导出，不恢复连续写卡。

### 真机复制超时与 RAWOUT 单帧隔离

诊断版在真机生成的 `R12S001.BIN` 为 `state=3`、`captured=1`、`torn=1`、`dual_error=0x2201`，复制后的序号为 `0x96`，源地址仍为 `0x85d1b800`。这确认同一源缓冲在 CPU 复制期间被后续帧覆盖；不是地址切换，也没有进入导出。继续重复同一复制流程没有诊断价值。

下一阶段改用 MIPU 第二路 RAW 输出，先只做一帧。`qemu/expeed6_mipu.c` 的研究模型在每个流帧完成前读取当前 RAWOUT 寄存器，并通过 `mipu_model_raw_out` 实际复制 RAW 到目标，再发出帧完成事件。修改模型后从 `qemu-expeed` 根目录运行 `bash apply_and_build_macos.sh`，同步到 `.runtime/qemu-9.1.0` 并重建实际使用的 `qemu-system-arm`；不要只编译另一份源码。通用 DMA 守卫默认拒绝写 `0xc1800000–0xc6100000` 的 RTOS 区，即使地址来自原厂分配器；因此首轮 RAWOUT 实验生成的近乎全黑文件是未初始化内存，不是有效捕获。只有帧事件而没有实际 DMA 写入时，不得验收。

该实验需要显式设置 `EXPEED_RAWOUT_PRIVATE=1`，才允许流 RAWOUT 写入上述 RTOS 区；默认行为和其他 DMA 守卫不变。此开关只用于私有缓冲模型实验，不是通用关闭安全检查：

```sh
export EXPEED_RAWOUT_PRIVATE=1
export MODULE=/absolute/path/to/Z62APP-rawout-single.BIN
bash out/raw12_qemu/start.sh
```

RAWOUT 单帧模块 SHA-256 `437b5d0f6cd5af258d4105e4ec5f0f3ffa88913a15a97356c72df1b6bd3442b2`，从录像开始后第 4 个帧完成事件起再检查几何并分配一个私有缓冲，设置 `RAWOUT_ADDR=buffer`、`RAWOUT_PITCH=3040`，只切换 `RAWOUT_CTL` 的 bit0。帧完成回调在原生处理之后记录目标和序号并立即关闭 bit0，不执行整帧 CPU 复制、不打开文件。停止原厂录像约 2 秒后才使目标缓存失效并导出一个 Z12，然后释放内存。

QEMU 实测 `state=2`、`captured=1`、`torn=0`、`rejected=0`、`exported=1`、帧完成时 `RAWOUT_CTL=3`，目标与私有缓冲地址一致。`R12S011.BIN` 无导出错误，两个分配指针在停止后归零。`RAW12005.Z12` SHA-256 为 `700e12a941495d5c5b5f2327a6a5e4ab13c36904e57c8df9e8b3f3a372aff98e`；导出的私有缓冲与 Z12 载荷逐字节相同，并与当前源地址每一行的 3,033 个有效打包字节完全一致。行尾 7 字节填充不属于像素，不参与该项比较。DNG 实际出图且与已验证单帧样本一致。同次 5.76 秒、1080p25 原厂 MOV 经 FFmpeg 完整解码通过。

真机状态诊断使用 `data[22]`：`0x2301` 为完成时 RAWOUT 控制/目标不匹配，`0x2302` 为序号不是下一帧，`0x2303` 为几何变化，`0x2304` 为初始源无效或 RAWOUT 已占用，`0x2305` 为等待帧超时。真机首次 RAWOUT 单帧测试生成了 `R12S000.BIN` 和 `RAW12000.Z12`：状态为 `captured=1`、`torn=0`、`rejected=0`、`exported=1`、无导出错误，帧序号 `0x73`，源地址 `0x85d1b800`。Z12 SHA-256 为 `ee3e7b3578875180df85ff90c6b0101a982ccb0df4fff9f9dfe4a5f4f9bd651c`，但 DNG 实际显示为异常高频量化纹理，与此前已验证的真机 RAW 明显不同，**不计为像素或真机功能通过**。

下一版在每行开头写入包含行号和字序的 16 字节唯一哨兵，DMA 前清理私有缓冲缓存，停止后先使缓存失效再检查所有行。若仍有哨兵，报 `0x2306`，`data[23]/data[24]` 保存首个未覆盖行号及其实际字，拒绝导出。只有所有哨兵被覆盖才写 Z12，之后仍须实际出图验证。该实验用于区分未发生 DMA 写入与 RAWOUT 格式/锁存时机问题；不得直接跳到连续写卡。

哨兵版 SHA-256 `84acd33c3c29639b868dfbc50e8f36686e32558e5d2916334943a5ae08b2b56c` 已在 QEMU 按更新后的门槛复验：启动完成提示后等待，再确认帧计数 `6735→6834` 增长后才录像。结果为 `captured=1`、`bad_row=0xffffffff`、`export_attempted=1`、`exported=1`，无拒绝或导出错误。所有 1138 行的哨兵均被覆盖，私有缓冲与 Z12 载荷一致，每行 3,033 个有效字节与源数据相同。`R12S012.BIN` 状态有效，Z12 SHA-256 为 `ff14804398eadecd6dd3467fe780730782358829dc9c40e3896e7b52fad3b71d`；同次 6.12 秒原厂 MOV 完整解码通过。

同一哨兵版在真机得到 `R12S000.BIN`，没有 Z12：`state=4`、`captured=1`、`rejected=1`、`dual_error=0x2306`、`export_attempted=0`。`data[23]=0`、`data[24]=0xa5000000` 正好是第 0 行第 0 字的原始哨兵，证明当前“录像中途启用 RAWOUT”的方式没有按模型覆盖私有缓冲。这里的 `captured=1` 只代表收到帧事件，最终状态已拒绝，不能解释为 DMA 成功。该启用时机不再上机重复；已成功的 CPU 单帧基线保持独立。

随后在 QEMU 对原厂 RAWOUT 寄存器写入做了只读跟踪（`EXPEED_TRACE_RAWOUT=1`）：切换视频后只观察到 `0x1036c364/36c/376` 写入 `CTL=2`、`ADDR=0xd467b400`、`PITCH=0x20`，开始录像没有再次配置。原厂 SHA-256 已核对的 `eg1850_mas_01700_stock.bin` 反汇编确认这些写入来自同一组固定寄存器初始化代码，行距常量 32 与模拟器的排空路径一致，不能直接当作录像 RAW 输出配置。它支持中途写入未进入活动任务的判断，但尚不证明真实寄存器的完整锁存语义，不能据此再生成一个盲试版本。

同时复核了 CPU 复制函数：`0x1035d254` 是 **ARM 状态**入口，源地址对齐时进入 `0x1035d1ec`，循环使用 LDM/STM 每次复制 32 字节，不是逐字节 memcpy。不能通过把它误当成低效实现来宣称轻易解决帧周期问题。下一步仅在模拟器检查 XDMAC 通道占用和并行复制可行性，不修改真机。

### XDMAC 通道 3 与 CPU 并行复制

录像中的三次 XDMAC 采样均确认 `XDACS=0x11000000`（全局使能开启），通道 3 的 `LEN/SRC/DST/GO` 均为 0。其他通道保留原厂配置，当前实验不使用它们。`raw12-dma-single` 只使用通道 3，并要求开始时 `GO==0` 且全局使能已开启；否则报 `0x2401`，不修改通道。

该实验把一帧按 569 行分成两个 `1,729,760` 字节半帧：通道 3 复制后半帧，原厂 ARM LDM/STM memcpy 复制前半帧。启动值 `GO=0x11109000` 来自观测到的原厂 `0x01109000` 加上软件请求和通道使能位。每行仍有唯一哨兵；源几何、帧序号、源地址、DMA 完成状态和全部哨兵均通过后才允许停止后导出。通道使用完恢复，失败时不释放仍有活动 DMA 的目标而不先停用通道。

QEMU 候选 SHA-256 `34d0657be1796ae81f145e8df4f7628e0cdfbb6e75e9fa40f5d6dfc224725708` 得到 `captured=1`、`torn=0`、`rejected=0`、`GO=0x01109000`、`STAT=8`、无未覆盖行，停止后 `exported=1` 且通道不再活动。`R12S013.BIN` 状态正确，Z12 SHA-256 为 `1e8c4516aa44cd57c4c9ae95e2328b19697172a98c832ba9c6f23d538e5bcceb`；**完整私有帧、源帧和 Z12 载荷逐字节一致**，RAW 载荷 SHA-256 为 `66da6079dcee35c6371d6af71cf72d86dbc5e9d58f06b05e3b7f83553361edeb`。DNG 正常出图，同次 4.92 秒原厂 MOV 完整解码通过。

`0x2402/0x2403` 分别为 DMA 完成状态错误和超时，`0x2404/0x2405` 为源/几何拒绝和帧序号缺口，`0x2406` 为哨兵未覆盖；后一种情况下 `data[23]/data[24]` 保存行号及实际字。QEMU 的 XDMAC 模型在写 `GO` 时立即完成内存复制，再按 100 MB/s 模拟完成延迟，不能证明真机的传输带宽、缓存一致性或时序。因此这里只证明复制路径、通道配置和数据结果在模型中成立；真机仍须先验证单帧，不能直接扩展到双帧或连续 RAW。

上述 DMA 辅助单帧在真机得到 `R12S000.BIN`，没有 Z12：`state=3`、`captured=0`、`torn=1`、`error=0x2201`、`GO=0x11109000`、`STAT=0x10000`。通道已经启动，但在下一帧到来时仍未完成，导出未启动。后续版本先启动后半帧 DMA，再只对 CPU 负责的前半帧做缓存失效，避免在 DMA 开始前失效整帧源。诊断细分为 `0x2211`（CPU 半帧期间序号变化）、`0x2212`（等待 DMA 时变化）、`0x2213`（DMA 完成后变化）；对应源地址变化为 `0x2221/0x2222/0x2223`。

缓存顺序优化版 SHA-256 `7c84d394e5eefc473a675b210b8e6e3e5850c0db88cb5931fb400ced5853ae13` 已通过 QEMU：`captured=1`、`torn=0`、`rejected=0`、`GO=0x01109000`、`STAT=8`、`exported=1`，全部哨兵被覆盖，完整私有帧、源帧和 Z12 逐字节相同。Z12 SHA-256 为 `c1dca07c186ebacc216b571d1c27c94222153a22b36a2bb4b32e073cc570e893`，同次 5.28 秒原厂 MOV 完整解码通过。

同一优化版真机 `R12S001.BIN` 为 `state=3`、`captured=0`、`torn=1`、`error=0x2212`、`GO=0x11109000`、`STAT=0x10000`，没有 Z12。这已经把瓶颈定位到等待 DMA：CPU 半帧已完成，但 DMA 在下一帧到来时仍忙，不能再通过调整 CPU 缓存顺序解决。

随后对原厂 XDMAC 写 `GO` 的只读跟踪发现，原厂软件请求启动值是 `0x11109003`，而此前实验漏掉了低两位中断使能。原厂 `0x10295f6c` 启动函数会执行 `ORR value, value, #3`，软件请求分支再设置 SE/CE；停止路径在 `0x10295e3c–0x10295e4c` 清 STAT 和 GO 低两位。四个通道的完成处理均存在，通道 3 注册项为 IRQ `0x13d`、处理器 `0x10295fa7`，未用回调为空。服务上下文 `0xc180675c` 的 `+0x18` 字节保存原生完成处理器记录的 STAT 低 4 位，下一字 `+0x1c` 保存传输长度，两者不能混用。新版使用原厂的 `0x11109003`，先检查注册项（不匹配则 `0x2407`），并接受硬件 `STAT=8` 或 `+0x18` 已确认的结果，避免原生 IRQ 已清 STAT 时误报 `0x2402`。每次启动前清零该状态字节，防止沿用上一次完成结果。

最终修正版 SHA-256 `3df0e90d755f71a6d0fa3e1473e34ba9aa3468d95e04089e39d22a1754d25ca0` 在干净实例中先确认 `MOVIE_ACTIVE=1`，随后得到 `captured=1`、`torn=0`、`rejected=0`、`exported=1`、`GO=0x01109000`、硬件 `STAT=0`，而 `0xc1806774` 的原生状态字节为 `8`。全部哨兵被覆盖，完整私有帧、源帧和 Z12 逐字节一致；Z12 SHA-256 为 `f458a8d953398096c97d52f2408efca55ec0a0f2831c33766731fc462f3f8a84`，同次 5.76 秒原厂 MOV 完整解码通过。此前没有 `MOVIE_ACTIVE` 的运行全部判为无效环境测试，未计入该结果。

同一版本的真机 `R12S000.BIN` 仍为 `state=3`、`captured=0`、`torn=1`、`error=0x2212`、`GO=0x11109003`、`STAT=0x10000`，没有 Z12。因此完成中断本身不是充分条件。进一步反汇编 `0x10295ebc` 和 `0x103a5e4e` 找到原厂完整描述符配置和同步复制封装：除 LEN/SRC/DST/GO 外，还有三项控制寄存器。实际录像采样中内存复制通道的这三项为 `0x30f00 / 0x30f00 / 0x0`，与原厂默认初始化 `0x103a5e98` 一致，而实验通道 3 原来为全零。后续实验补齐这三项并恢复原值，保留 CPU 半帧、帧序号检查、哨兵和完成中断。

完整描述符版本 SHA-256 `e5eee8dd2ed5821af42a8a40e902aecc7f6b57b74217f2775d8cd869fb3d6e51` 已在 QEMU 确认 `MOVIE_ACTIVE=1`、`captured=1`、`torn=0`、`rejected=0`、`exported=1`、原生完成状态 `8`。全部哨兵被覆盖，完整私有帧、源帧和 Z12 逐字节一致；Z12 SHA-256 为 `aef45d30429cd69cc91118c7630e299e2ea60044736dfe9528f6839986649319`，同次 8.40 秒原厂 MOV 完整解码通过。

**同一模块已在真机普通 1080p30 通过单帧验证。** `R12S000.BIN` 为 `state=2`、`captured=1`、`torn=0`、`rejected=0`、`export_attempted=1`、`exported=1`、无导出错误；帧序号 `0x57`、源地址 `0x85d1b800`。`RAW12000.Z12` SHA-256 为 `46d29ee2e57f6a70972accb00ff0a2409af583e1e0c6aa04b7dd1c9a832f021c`，解包样本范围 252–4095、均值 611.311、3,844 个不同码值。DNG 已实际出图，可辨认真实桌面场景，DNG 与 Z12 解包像素的 SHA-256 均为 `9c7ba9895c2d6ad6fc96081a5707e1a2565145510c1cff60f0df0f9b45ece7b2`。DNG 仍使用未校准恒等色彩矩阵，暗绿色预览不代表已完成色彩校准。

这一结果证明完整的 XDMAC 描述符配置、CPU 半帧、原生完成中断和停止后导出可在所测真机短录中工作，冻结为新的 DMA 单帧基线。它不证明双帧、连续复制或并发写卡安全；后续扩展必须继续保持独立缓冲、帧完整性检查和停止后导出。

### DMA 连续两帧

在真机单帧基线之上，`--raw12-dma-dual` 使用两块独立内存，逐帧复用同一套 DMA 半帧＋CPU 半帧和完整描述符。第二帧序号必须等于第一帧加一，通道每次使用后恢复，停止后分别验证两块缓冲的全部哨兵；任一失败都不导出。第二帧哨兵错误为 `0x2408`，第一帧仍为 `0x2406`。

QEMU 模块 SHA-256 `ea45a168db060fbbba77b033c2ed590b94dfde5754f8892adc61937ae38eb7b2` 产生 `R12S018.BIN`：`state=2`、`captured=2`、`torn=0`、`rejected=0`、`export_attempted=1`、`exported=1`，两块申请第一轮成功，`data[25]=0x00010000`。`RAW12010.Z12` 为 6,919,136 字节，序号 `0x12a2/0x12a3` 连续，两个源地址均为 `0x82c00000`，两个帧载荷 SHA-256 均为已验证的 `66da6079dcee35c6371d6af71cf72d86dbc5e9d58f06b05e3b7f83553361edeb`。Z12 SHA-256 为 `1d490e3f3361f915879876c59135d3fdf74ebcf18cf31ebe538c7b1ded912217`，两个 DNG 均实际出图且一致，符合静态场景预期。该轮两个原厂 MOV（8.40 秒和 20.40 秒）均完整解码通过；多次触发产生的两段文件不作为严格单次时序证明。

固定 1 秒检查曾得到 `MOVIE_ACTIVE=0`，但随后实际启动并生成双帧文件，因此启动等待已改为最多 15 秒轮询，未观察到激活时不追加停止键。真机双帧尚未验证，连续 RAW 写卡仍未恢复。

共享目标缓冲后的单帧回归模块 SHA-256 `a74db84633d81b1ad55c64c4276b9250657b0685237f6f5e8a2cb95d76aa83c5` 也通过 QEMU：`captured=1`、`torn=0`、`rejected=0`、`exported=1`，完整私有帧、源帧和 Z12 逐字节一致，Z12 SHA-256 为 `a1aa6c526ee7c8815256b9936e4c353bb99aea1e683e006107bc4bee28c177f7`，同次 6.60 秒原厂 MOV 完整解码通过。已通过真机的单帧基线文件不因此替换；双帧实验使用独立测试目录。

**DMA 连续两帧模块 SHA-256 `ea45a168db060fbbba77b033c2ed590b94dfde5754f8892adc61937ae38eb7b2` 已在真机普通 1080p30 通过。** `R12S000.BIN` 为 `state=2`、`captured=2`、`torn=0`、`rejected=0`、`export_attempted=1`、`exported=1`，两块申请第一轮成功，无导出错误。`RAW12000.Z12` 为 6,919,136 字节，SHA-256 `fd0eb3c798103d37bcef21268bd7423e25d79dd2251f1a4faaaf7aca9e229e60`；两条序号 `0x6f/0x70` 连续，源地址均为 `0x85d1b800`。两个帧载荷哈希不同，实际有 2,112,885/2,301,036 个样本值不同，排除了重复输出同一缓冲。两个 DNG 均正常显示实景且与各自 Z12 解包样本逐项一致；色彩矩阵仍未校准。

这证明连续两次完整复制、独立缓冲、序号检查和停止后双帧导出可在所测真机短录中工作。下一阶段先做 4 帧内存短连拍，不直接恢复连续写卡。

### DMA 4 帧内存短连拍

`--raw12-dma-burst4` 使用四个独立帧缓冲，按 `pool0/pool1/pool0/pool1` 分配，复用同一套 DMA 半帧＋CPU 半帧、完整描述符和完成中断。四帧必须连续，停止后逐缓冲验证哨兵，再写一个 Z12；任一帧失败整组不导出。第 N 帧哨兵错误为 `0x2500|N`，N 从 0 开始。

QEMU 模块 SHA-256 `1e50d84108de43731424a6f0f2b749d3c342e702e199282d7c99ffb336165cac` 得到 `captured=4`、`torn=0`、`rejected=0`、`exported=1`，第一轮分配成功，四块缓冲地址 `0xc2d4fe80 / 0xc3c63080 / 0xc309c8c0 / 0xc3fafa80`，范围互不重叠。四条序号 `0xf0b/0xf0c/0xf0d/0xf0e` 连续，源地址均为 `0x875a9400`。`R12S020.BIN` 无导出错误。

`RAW12012.Z12` 为 13,838,208 字节，SHA-256 `87152eefe5e16ee373787a9cbbc4dfde345761b3e6a37a711a6b4a4c3c140817`；四个帧载荷均与源帧逐字节一致，SHA-256 均为 `66da6079dcee35c6371d6af71cf72d86dbc5e9d58f06b05e3b7f83553361edeb`。四个 DNG 均实际出图，符合静态场景；同次 9.72 秒原厂 MOV 完整解码通过。该模式仍是有限内存短连拍，不是连续 RAW 视频写卡。真机内存压力、复制时序和实际画面尚待验证。

真机 4 帧模块 SHA-256 `1e50d84108de43731424a6f0f2b749d3c342e702e199282d7c99ffb336165cac` 生成 `R12S000.BIN`，状态为 `state=2`、`captured=4`、`torn=0`、`rejected=0`、`export_attempted=1`、`exported=1`，无导出错误。`RAW12000.Z12` SHA-256 为 `a0d82b309310cfbca0b00b93fea9c21e08c56331a07ef0e88129fd53095e89d8`，四条事件序号 `0x7d/0x7e/0x7f/0x80` 连续，源地址均为 `0x85d1b800`。前三个载荷哈希不同，**第 4 个载荷与第 3 个逐字节完全相同**（均为 `b9aa79224d16a3687f2e08f43c893d3602a6cab9a7e2020e7999b73e2563f4c3`），对应 DNG 也完全相同。四幅预览都能正常显示实景，DNG 与各自解包像素一致。

因此该测试证明四次连续采集、独立缓冲和停止后导出成功，但不证明四个不同的传感器帧。当前 `status & 0x1000` 的事件计数不能直接等同于 RAW 输入新鲜度。原厂 `0x102e719a` 中断处理会检查 `status` 的 bit1，并在满足条件时推进后续处理，另一个观测合同把普通完成状态记为 `0x1002`。下一步先核实 `0x1002` 与输入完成的关系，不能直接扩大为连续视频。

### RAW 输入完成事件对照

针对真机 4 帧末两条内容完全相同的现象，DMA 路径改为只在 `(status & 0x1002) == 0x1002` 时推进帧序号；原 CPU 单帧/双帧路径保持 `status & 0x1000`，不改变已验证行为。原厂 `0x102e719a` 的 bit1 检查与后续消息处理是这一对照的依据，不能把任意 `0x1000` 都直接称为新 RAW 输入完成。

QEMU 提供显式 `EXPEED_RAW_FRAME_COMPLETE=1`，在流帧完成状态中加入 bit1，用于测试这条路径；默认模型行为不变：

```sh
export EXPEED_RAW_FRAME_COMPLETE=1
export MODULE=/absolute/path/to/Z62APP-dma-burst4.BIN
bash out/raw12_qemu/start.sh
```

对照模块 SHA-256 `1dc00833d53f70fcab25133b67f80c2d16e045e80a4d58a04290146f3524e072` 得到 `captured=4`、`torn=0`、`rejected=0`、`exported=1`，序号 `0x12a6/0x12a7/0x12a8/0x12a9` 连续，最后状态为 `0x1002`。`R12S021.BIN` 无导出错误。`RAW12013.Z12` SHA-256 为 `f7d6b50fd6debf0a6acd53b188bf7a979b9c18c421c70077903c134866d07a2c`，四个帧载荷均与源帧逐字节一致；同次 8.04 秒原厂 MOV 完整解码通过。

这只能证明人工加入的 `0x1002` 可驱动模型采集链，不能证明真机存在该事件。真机 `R12S000.BIN` 显示 `notifications=2601`，但 `frames_0x1002=0`、`captured=0`、所有几何/分配字段均为 0，且没有 Z12。**真机录像中没有出现 `0x1002`，该替代事件假设排除。** 不再用人工模型事件推断真机输入完成语义。

已恢复所有路径的 `status & 0x1000` 判定，4 帧模块重建后 SHA-256 恢复为已验证的 `1e50d84108de43731424a6f0f2b749d3c342e702e199282d7c99ffb336165cac`，测试目录也同步恢复，不保留无输出的 `0x1002` 版本。

随后用同一次真机录制做了 RAW/MOV 对照。Z12 SHA-256 为 `8031a5add4087ed56806009e5e09f3e2df43bcebba4f5b570064275c9e7ca1f6`，序号 `0x6f/0x70/0x71/0x72` 连续，前三个载荷不同，末两个载荷再次完全相同（`0f6e631798218b33caa0097178e509cb52deb86b3ff37dca2d761e8bb822a1c9`）。同次原厂 MOV 为 5.005 秒、30000/1001fps、150 个解码帧，FFmpeg 全帧解码和 framemd5 检查没有发现逐字节完全相同的帧。另做了缩小灰度图相关性、连续帧预览和 Z12/DNG 对照；画面运动和编码差异使帧映射不能仅凭这些指标唯一确定。

**结论是重复确实存在于 RAW 数据源，而不是导出器重复写同一缓冲；但仅凭 H.264 无完全重复帧，不能判定采集时机错误，也不能证明传感器没有重复。** 后续有限连续写入应保留这些重复帧并记录事件序号，不得为制造连续性而删帧。原始 MOV、Z12 和状态文件均已按同次录制验收，未再把 `0x1002` 当作真机可用替代事件。

### 8 帧有限连续写入

`--raw12-dma-stream8` 引入独立写入任务。前 4 帧先进入内存，写任务随后按序验证哨兵、写帧头和像素；后 4 帧继续采集，文件创建和 Z12 头在记录首帧序号前完成。每个槽有 EMPTY/CAPTURING/READY/WRITING 状态，未写出的槽不能被覆盖。只有 8 帧全部写完且文件关闭成功才设置 `exported=1`，重复帧按事件序号原样保留。

4 槽首版在写出前 4 帧后，第 5 次采集出现 `0x2405` 序号缺口；把开文件提前仍复现，说明启动余量不足，不能靠允许丢帧解决。随后把队列扩大到 8 个独立槽位，首批 8 帧不需要复用或覆盖任何槽。

最终 8 槽模块 SHA-256 `6d36cc5de35213c465dbfacb2f79174c9496f3b3ab423ac7b6f91c00d291d675` 在 QEMU 得到 `captured=8`、`torn=0`、`rejected=0`、`write_index=8`、`writer_done=1`、`exported=1`，序号 `0x139c/0x139d/0x139e/0x139f/0x13a0/0x13a1/0x13a2/0x13a3` 连续，文件正常关闭且无写入错误。`R12S024.BIN` 的 `data[18]=8` 同时确认写出帧数。

`RAW12016.Z12` 为 27,676,352 字节，SHA-256 `ed70612a1a4fabd807bfb31ada0c5a642d1ce80d3d6d763fe5db41951f5306d8`；八个帧载荷均与源数据一致，SHA-256 均为 `66da6079dcee35c6371d6af71cf72d86dbc5e9d58f06b05e3b7f83553361edeb`。八个 DNG 均正常出图，同次 4.80 秒原厂 MOV 完整解码通过。此结果证明有限帧数下并行写任务、槽状态、文件完成和原厂短录可以共存；**尚未验证真机并行写卡，也未验证槽复用和无限连续录像。**

**8 槽有限写入已在真机普通 1080p30 通过。** 模块 SHA-256 `6d36cc5de35213c465dbfacb2f79174c9496f3b3ab423ac7b6f91c00d291d675` 产生 `R12S000.BIN`：`state=2`、`captured=8`、`write_index=8`、`writer_done=1`、`export_attempted=1`、`exported=1`，无拒绝、撕裂或写入错误。`RAW12000.Z12` 为 27,676,352 字节，SHA-256 `1490836f067fde13d432352a6d9e8f632037053287ceb34eb17be827c99e99ae`，序号 `0x2f0/0x2f1/0x2f2/0x2f3/0x2f4/0x2f5/0x2f6/0x2f7` 连续。八幅 DNG 均为有效实景。

第 3/4/5 帧相同、第 7/8 帧相同，与之前 RAW 数据源重复现象一致，不是写任务重复输出。该结果确认真机并行写卡、8 帧连续记录和正常关闭可行；下一阶段复用这 8 个槽写入 16 帧，检查写任务追赶和槽生命周期，不直接跳到无限连续录像。

### 16 帧环形复用与刷新诊断

`--raw12-dma-stream16` 保持 8 个独立槽位，但总共写入 16 帧。槽被写完后才能复用，重复帧按事件序号保留。写入任务在首帧就绪后立即开始；只对该段首帧执行完整哨兵检查，后续仍检查槽状态、帧序号和源地址，并在电脑端逐帧验收。文件分块从 64 KiB 改为 256 KiB，减少 API 调用次数，其他模式保持 64 KiB。

前一轮只写出 9 帧，日志显示正常采集间隔约 40 ms，而第 10 次复制前出现约 109 ms 等待并跳过一个序号，证明是写入积压，不是主动丢帧。随后即时写入推进到 10 帧，仍出现后续复制竞争。256 KiB 分块与干净虚拟卡的组合实验完成了 16 帧；**没有单独分离两个因素各自的贡献**。环境上，旧卡归档为 `out/raw12_qemu/card-research-archive.img`，新卡只包含当前模块，避免空间不足和大量历史文件影响复现。

最终模块 SHA-256 `7d1e6006def64acc7fb0419beeb26a77a1be60cdc9c7d99d085155a53c6e4931` 得到 `captured=16`、`torn=0`、`rejected=0`、`write_index=16`、`writer_done=1`、`exported=1`，无写入错误，序号 `4204–4219` 连续。`RAW12000.Z12` 为 55,352,640 字节，SHA-256 `686e664fbde1491fcba86f4bec8932710defd5141b588693fc3df50c43963fe2`，16 个帧载荷均与源数据一致；16 个 DNG 正常出图，同次 6.12 秒原厂 MOV 完整解码通过。

诊断日志实际文件名为 `P12Sxxx.BIN`，含 32 条通知、16 条复制采样和 48 MHz 时间戳。每条复制记录包含序号、时刻、源地址和开头/中间/末尾各 16 字节采样，用于真机分析“通知过早、同一缓冲多次读取或原厂重复”。它不是传感器帧号证明；真机仍需用该日志和完整帧内容判断刷新关系。

### 真机 10 帧结果与显式缺口记录

真机首轮 16 帧实验只生成 10 帧，`RAW12000.Z12` 为 34,595,424 字节。状态为 `captured=10`、`write_index=10`、`error=0x2405`、`exported=0`。诊断日志显示第 10 次成功写入后，下一次复制序号从 559 跳到 561，漏掉 560，间隔约 68.483 ms；这属于写入积压造成的事件缺口，不是 256 KiB 分块被文件 API 直接拒绝。

同一份日志进一步支持 RAW 刷新不匹配：多个通知读到相同地址 `0x85d1b800` 的相同采样和完整载荷，重复并不只发生在导出端。前次事件日志混有 `0x4/0x8/0xa/0x800` 等非帧状态，后续已过滤为 `status&0x1000`，避免错误对齐。

新版 SHA-256 `fd86b7df7614549150edc8cbcdb0d09dd4be6c923139b579c53cf00e4cf0f2aa` 在 16 帧实验中遇到向前跳号时，保留真实帧序号并累计 `raw12_stream_dropped`（状态 `data[23]`），不再把缺失误报为连续，也不因一次缺口放弃整段。序号倒退仍拒绝，复制期间撕裂仍不导出。这里的 dropped 是未捕获的 MIPU 通知数，不能直接等同于传感器丢帧数。

QEMU 回归完成 16 帧，`captured=16`、`write_index=16`、`dropped=0`、`exported=1`，无非帧日志混入。Z12 SHA-256 为 `5d31f2cd68d70526d4278f459197c38dbf347eada013e642931245b14b95b492`，同次 5.76 秒原厂 MOV 完整解码通过。真机刷新关系与写入吞吐仍须复验，不能据此宣称无限连续录像已经实现。

### 分批排空与 1 MiB 分块回退

真机下一轮 16 帧实验仍为 10 帧，但错误变为 `0x2211`：第 11 次 CPU 半帧复制期间跨帧。复制间隔在最后一次约 60.362 ms，且重复采样仍存在。这是持续复制与写入竞争，不是简单序号缺口。

另一次把分块增到 1 MiB 的实验虽生成 16 帧，但原厂 MOV 只剩短片段，不能作为正常录像证明，未进入真机候选。缓存维护函数在超过 `0x45000` 字节时进入更重的处理路径，256 KiB 恰低于该阈值，因此恢复 256 KiB，不再扩大分块。

最终采用 **8＋8 分批**：前 8 帧采集完成后，先等写任务排空这 8 个槽，再记录真实事件缺口并继续后 8 帧。模块 SHA-256 `013e38b64168591817265be1a75bbb61c16208966ba5ee7ea1a5453da94bd84a` 在 QEMU 完成 16 帧，`captured=16`、`write_index=16`、`dropped=1`、`exported=1`，没有复制撕裂或写错误。帧序号为 `4948–4955, 4957–4964`，缺失的 `4956` 与 `data[23]=1` 一致。Z12 SHA-256 为 `2260c27d20f72a5f5ece03fb49339efe2f25ededf254de09568168aa41dd3788`，同次 5.76 秒原厂 MOV 完整解码通过。该方案明确保留写入缺口，不宣称无丢帧的 30fps 连续录像；真机需要验证分批复制、写入和原厂 MOV 是否都可接受。

**同一模块在真机完成了 16 帧，但有明显吞吐瓶颈。** 状态为 `captured=16`、`write_index=16`、`dropped=22`、`exported=1`，无复制撕裂或写错误。Z12 为 55,352,640 字节，SHA-256 `bc98bf271d8a0c3e21cc400a036bc5d1bbcc0b3622101c5d5f331274c75acce4`，序号为 `51–58, 81–88`，缺少 59–80 共 22 个通知。两批之间的复制时间差约 770.317 ms，而普通帧间隔约 33 ms，说明写任务排空首批 8 帧花费了远多于连续采集的时间。16 个 DNG 均为有效实景，因此这是**可写出但无法保持连续 30fps 的有限结果**，不能宣称连续 RAW 视频已实现。

该结果直接证明真机写路径存在吞吐瓶颈，但尚不能区分 SD 卡/文件系统上限与 CPU/缓存/任务竞争。下一步用相同 256 KiB 分块、相同文件 API 和 48 MHz 计数器做独立写速基准，再决定是否能支持连续采集。

### 相机文件系统写速基准

`--write-bench` 不读取 RAW，只在非录像状态分配 1 MiB 缓冲，按固定测试图案写入 64 MiB，使用与 RAW 实验相同的文件 API 和 256 KiB 分块。它记录 48 MHz 计数器的开始、数据写入结束和文件关闭时间，并保留实际写入字节数、错误码和分块大小。状态文件实际命名为 `B12Sxxx.BIN`，数据文件为 `BENCHxxx.BIN`。

QEMU 模块 SHA-256 `82c38eb07703ac8614e9457fa7c9c7e2e62cafef9db4b48a9e29cd57ff62899a` 已完成验证：64 个 1 MiB 块内容与测试图案逐字节一致，`written=67,108,864`，写入/关闭均返回 0。数据阶段耗时 `24,244,818 ticks`，总耗时 `26,276,186 ticks`，折算数据阶段约 **132.862 MB/s**、总阶段约 **122.591 MB/s**。这些数字只描述模拟器文件后端，不能作为真机速度。

真机测试时先备份当前 `Z62APP.BIN`，替换为基准模块，保持非录像状态启动约 15 秒，然后读取 `B12Sxxx.BIN`。数据字段为：`data[2]` 阶段（0 成功）、`data[3]` 数据阶段 ticks、`data[4]` 总 ticks、`data[5]` 文件句柄、`data[6]` 写入结果、`data[7]` 关闭结果、`data[8]` 48,000,000、`data[9]` 262,144、`data[10]` 64、`data[16]` 实际字节数。换算为 `实际字节数 × 48,000,000 / ticks`。测试后换回原模块；`BENCHxxx.BIN` 可按需要删除。

## 验证边界

固件打包会执行原包 K8 验证、主模块 CRC、包 CRC、重签、重新解密和目录逐成员比对。QEMU 可验证启动、读卡、模块初始化和回调安装，但其录像编码与真实硬件计时不完整，不能据此宣称真机已突破 29:59。最终仍需真机录像验证。

## 其他已排除的方法

`gphoto2 --set-config movie=1` 虽可触发录像，但屏幕时间显示 `--m--s`，后台原厂计时仍照常运行，到 29:59 仍会自动停止；这不是破解路径。
